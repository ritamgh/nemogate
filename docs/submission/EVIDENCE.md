# Evidence index

This file maps the headline numbers on the results page (https://ritamgh.github.io/nemogate/) and in `docs/submission/DEVPOST.md` to the file each one comes from. It lists 127 claims in nine sections. The first four sections follow the page: headline, then one section for each of the three rules in the main set. After those come cost of prevention, the held-out appendices, the second app, recall and coverage, and the numbers that are in DEVPOST but not on the page.

Every value in the tables was formatted by a script from the source file, in the same way the page formats it (percentages round half up, p values print as `%.3g`, costs as `$%.3f`). The script then looked for the same value in the page text, and in DEVPOST for the claims it names. Where a value is not on the page or cannot be sourced, the row says so, and the Mismatches section lists it.

Scope: this indexes the headline numbers and the per-cell tables behind them. It does not list every number on the page.

## How to rebuild the main results file

The five sweep folders of the main set are in the release `evidence-2026-10-27` (asset `nemogate-runs-t6-t10-t11.tar.gz`). The page's `results.json` is rebuilt from them with the pins below. The T14 and T13 results of the second app are in `results/research/t14.json` and `t13.json` and can be read directly.

```
tar xzf nemogate-runs-t6-t10-t11.tar.gz
uv run python -m replay.stats runs/sweep-2026-10-19 runs/sweep-2026-10-19-t10b runs/sweep-2026-10-19-t11b runs/sweep-2026-10-19-t11c runs/sweep-2026-10-19-t11d --ledger nemogate.yaml --repo-sha T6=b0736bb4da66 --repo-sha T10=f06137eaf4a6 --repo-sha T11=0186900aa6bf --out results.json
uv run python -m replay.audit runs/sweep-2026-10-19 runs/sweep-2026-10-19-t10b runs/sweep-2026-10-19-t11b runs/sweep-2026-10-19-t11c runs/sweep-2026-10-19-t11d
```

- Without the three `--repo-sha` pins, 182 runs are counted instead of 179.
- sha256 of the tarball: `a42b095d76cb596aeb9a65410b8262ba16051283aad66bcac6db5bc035b2e2f2`.
- sha256 of `results.json`: `63d7c24abd57741bed29833dedcae691d066ec98a9663f3f673ca4de372419ef`. The rebuild command above produced a file with this same hash when this index was written.
- The audit reads 280 runs. 278 match their saved record and 2 differ. The 2 are T11 forks at commit b0736bb4da66, which is not a T11 commit pinned above, so they are in no T11 rate.
- `results.json` is also public as a release asset: https://github.com/ritamgh/nemogate/releases/download/evidence-2026-10-27/results.json.

## How to read the tables

- **Value as published**: the text as it appears on the page (or in DEVPOST), formatted from the source.
- **Where it appears**: the page section, then the DEVPOST lines, as `docs/submission/DEVPOST.md` stands on `main` after PRs #110 and #113. A line may state the value in other words (for example "+38 points" for "+38 pp"). "not stated" means DEVPOST does not carry that value.
- **Source file and path**: a JSON path inside `results.json` (`constraints[<rule>].boundaries[<handoff>].cells[...]`, `.comparisons[...]`, `.exact_tests[...]`) or another file.
- **Denominator**: what n counts. A "whole run" is one full run of the agents. A "fork" is a run that continues from a saved point of a source run, so only the part after the fork point is new.
- **Independent sources**: `n_sources`, the number of different source runs the cell was built from. Forks of one source are not independent of each other.
- **Test**: how the interval or p value is made, from `replay/stats.py`. Whole runs of two arms with nothing in common use Fisher exact. Forks that share sources use McNemar exact on matched pairs, and a sign test over sources for the "counting each source once" p value. Rates have Wilson 95% intervals. Differences use a Newcombe interval, which treats the two cells as independent samples.

## Mismatches

These are places where the page, DEVPOST and the files do not agree, or where a claim has no file behind it. Nothing was changed to hide them.

1. **Rules in the ledger: 8 on the page, 9 in the files.** The page's coverage table says 8 rules declared, 8 of 8 with a compiled check, and "8 of 8 rules can be graded". The rebuild command with today's `nemogate.yaml` gives `honesty.constraints_total` 9 and `constraints_with_check` 9, because the second app's rule C-011 was added to the ledger after the sweeps (commits f539c11 and 610d056). Rebuilt with the 8-rule ledger from before those commits, `results.json` says 8, and every other field is identical. `t13.json` and `t14.json` also say 9. So the page's 8 matches the ledger at the time of the sweeps and not today's file.
2. **Extraction recall is not in `results.json`.** `honesty.extraction_recall` is null there. The page gets 22 of 30 and 11 of 24 from `results/recall/dev.json` and `reference.json` through `report.site --recall`. `replay.stats --extraction-recall` does not accept those two files.
3. **Resolved (PR #110 merged).** **DEVPOST on main and PR 110 differ in one number.** Main says "held-out cells have 5 to 6 runs". PR 110 says "1 to 6 runs per cell", which is what the page's limits tile says. The first-run appendix has cells of 1 to 6 runs and the re-run appendix 2 to 5, so main is out of date. The other PR 110 changes are wording and dates (republished 2026-10-27, only `drop` run live, link text, the second-app row now pointing at Appendix 3 and 4), not numbers.
4. **Resolved (PR #110 merged).** **Stale source column on main.** The DEVPOST "where each number comes from" row for the second app (0 of 33 vs 10 of 32, p = 0.0078) still says "PR #102 description; not yet on the results page". The page now carries it as Appendix 3, and the numbers match `t14.json`.
5. **Repair numbers: "on T11" is not stated by the repair output.** DEVPOST says 45% → 44% and 90% → 88% are "on T11". The page says the repair output does not state which rule, arm and operator. `PROJECT_CONTEXT.md` says the repair ran on T11 natural, and the baseline matches the T11 natural cell (9 of 20 broke, 18 of 20 passed). The summary file was written by hand from a run log that is not in the repo (`docs/SPEC.md`).
6. **T10 step-limit note.** "Six more natural runs stopped at the 60-step limit" is confirmed from the run folders (6 natural T10 runs at commit f06137eaf4a6 carry the recursion-limit error). "At least 3 of them had already broken the rule" is not in `results.json`; it is derived by `report/step_limit.py` in `results/step-limit-sensitivity.md` (PR #111), which judges the rule on each partial trace (3 of the 6 violate it).
7. **C-008 re-grade note.** "1 of 20 block-only forks broke the rule by emptying the file" has no file in the repo. The page itself says it is not part of the results file. The script that made it is outside the repo.
8. **T14 error types.** 20 overloaded (529) responses and one timeout is recorded in the message of commit 9a10993, which says it was checked against the saved `error.json` files. Those T14 run folders are not in this checkout, so this index did not re-derive it. Only the per-arm error counts (6, 8, 7, 0 = 21) are in `t14.json`.
9. **Intervals on differences.** The Newcombe intervals for differences (for example +38 points, +2 to +63, for T6) treat the two cells as independent samples. That fits the T6 whole runs. It does not fit T14, where the mutated forks continue natural source runs, and it does not fit the gated against block-only differences for forks of the same sources. The exact tests in the same tables do use the pairing.

11. **Price labels.** `docs/FACTS.md` lists the helper model prices under the name Nano. `config.yaml` holds them under Lightning (0.06 / 0.24). DEVPOST uses the `config.yaml` values.
